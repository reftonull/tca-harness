# isowords: integrate an existing app

This example embeds the harness in [Point-Free's isowords](https://github.com/pointfreeco/isowords), using its original **AppDelegate → Store<AppReducer> → AppView**. Navigation, the cube renderer, word validation and scoring run through upstream reducers and views.

[Watch the recorded game](recordings/actual-isowords-gameplay.mp4) · [Final screen](recordings/actual-isowords-final.jpg) · [Execution transcript](recordings/actual-isowords-gameplay.jsonl)

The recorded run opened Solo → Unlimited and submitted **SUN for 12 points**. No coordinate taps were used. Replay uses a random puzzle, so the word and score can differ.

## What's in this directory

| File | Role |
| --- | --- |
| [EmbeddedIsowordsHarness.swift](EmbeddedIsowordsHarness.swift) | Typed descriptors and a runtime attached to the original store |
| [app-entry.patch](app-entry.patch) | Small entry-point change to retain/start the attachment |
| [setup.py](setup.py) | Fetch and prepare the pinned source, embed the adapter, generate the project |
| [upstream.py](upstream.py), [client-pins.json](client-pins.json) | Compatibility preparation for this upstream revision |
| [play_word.py](play_word.py) | Drive the app through the CLI client and verify a scored move |
| [run_goals.py](run_goals.py) | Bounded multi-capability agent goals, state verifiers and latency reporting |
| [recordings](recordings) | Evidence from the verified run |

Upstream source is fetched into `.upstream/`, which is ignored by Git. Only our integration code, setup recipe and demonstration artifacts are committed.

## Run it

Tested with Xcode 26.4.1 / Swift 6.3 and an iOS 26 simulator. Install Python 3.10+, Git LFS, XcodeGen and FlowDeck first. Setup uses `/usr/share/dict/words`; supply `--words /path/to/words.txt` if unavailable.

From the repository root:

```sh
python3 examples/isowords/setup.py
cd examples/isowords
flowdeck config set -w IsowordsEmbedded.xcodeproj -s IsowordsEmbedded -S 'YOUR_SIMULATOR'
flowdeck build --config flowdeck.json
flowdeck run --config flowdeck.json --no-build --launch-env TCA_HARNESS=1
```

Select an installed simulator name or UDID in the configuration step. An existing isowords checkout can be supplied with `setup.py --source /path/to/isowords` to reuse Git objects and populated assets; that source checkout is read only. Setup refuses an unexpected revision and is repeatable for the prepared checkout.

The adapter retains a single `StoreHarness` created with `store.harness(descriptor:)`; the attachment owns runtime and transport.

The listener is opt-in through `TCA_HARNESS=1` and uses port **8767**. From the repository root, no model credentials are needed to inspect it:

```sh
./scripts/tca doctor --port 8767
./scripts/tca inspect --app --port 8767
./scripts/tca observe --app --port 8767
```

Setup also applies `.harnessTimeline()` to the root reducer. To watch the app's actions, effects and state while you play or while an agent runs:

```sh
./scripts/tca devtools --port 8767   # open http://127.0.0.1:8780
```

For the model-driven replay, configure [Router credentials](../../cli/README.md#model-driven-goals), launch a fresh app, then run:

```sh
python3 examples/isowords/play_word.py
```

## What the recording demonstrates

1. Jev selects the Home/Solo navigation and Unlimited mode operations.
2. A deterministic search outside the app finds a valid word/path from the observed board and dictionary.
3. Jev selects each exposed cube-face operation. The runner mechanically dispatches gesture release.
4. Jev submits the selected word; the runner verifies the accepted word and positive score in the real game state.

This demonstrates package integration and execution through TCA. The word search is not performed by an LLM. The example exposes a gameplay slice; it does not claim complete operation coverage of isowords.

## Complex agent goals

Launch a fresh app, then run:

```sh
python3 examples/isowords/run_goals.py > /tmp/isowords-goals.jsonl
```

The suite exercises Home and in-game Settings, enum/boolean binding actions, schema-constrained numeric arguments generated by Haiku, navigation through nested presentation reducers, recovery from a partial word selection, three distinct scored words, and leaving/resuming a game. It also probes unsupported typing and reuse of a dismissed feature's candidate. Each goal has a bounded execution loop and checks actual reducer state; a dispatch receipt alone does not prove completion.

[Interactive run explorer](recordings/interpretable-run.html) · [Results and limitations](GOALS.md) · [Latest report](recordings/complex-goals-report.json) · [First-pass report](recordings/complex-goals-first-pass-report.json)

To explore a new transcript, run `./scripts/tca trace --input /tmp/isowords-goals.jsonl` and open the resulting file. The explorer includes goal outcomes, model inputs and alternatives, action arguments, receipts, observed state changes, and timing.

Goals and success predicates are written by us. Jev chooses available operations; Haiku supplies numeric arguments. The word planner searches the bootstrap dictionary and observed face geometry, replans after each accepted word, and asks Jev to select the resulting face actions. Gesture release is dispatched mechanically. This is a reproducible capability exercise, not an unrestricted autonomous planning benchmark.

The suite also attempts an out-of-range music volume and checks that schema validation rejects it without mutating state.

The runner waits for renderer readiness instead of asking the classifier to act while the game is loading. Its default 0.8-second pacing gives upstream presentation animations time to settle; this is included in end-to-end goal duration but excluded from individual model/RPC timings. A separate three-second settling delay before resume works around an observed upstream transition/lifecycle race; it is configurable with `--transition-delay` and is not a generic completion signal. Resume checks in-memory state within the running app, not persistence across launches. The offline mock settings dependency does not promise settings persistence across recreated Settings reducers. Settings goals verify reducer values; no-op audio and settings-stream dependencies do not demonstrate audible volume or persistent app-wide appearance changes.

## Fixture boundaries

Harness mode uses offline API, Game Center, notification and purchase dependencies; in-memory SQLite/settings; and no-op saved-game files. Onboarding is skipped. Dictionary lookup, puzzle generation, selection rules, scoring and rendering remain upstream implementations. The public-bootstrap dictionary comes from the system word list; it is not the proprietary production dictionary. Fonts fall back to system fonts and audio is disabled.

The checkout is pinned to `c727d3a7c49cf0c98f2fa4f24c562f81e30165f7`. Setup applies dependency/compiler adjustments and fixes directory creation for SQLite's `:memory:` URL on current Foundation. Home, Solo, Game, AppReducer and their views are unchanged.
